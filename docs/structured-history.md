# Структурированная история

Реализовано 2026-11-06. Формат принадлежит Minerva; Rig, Codex и assistant-ui адаптируются на границах.

## Ответственность и контракты

- `transcript.rs`: упорядоченные части ответа, типизированные payload `ToolCall`/`ToolResult`, проверка связей. Не знает SQLite, Rig, Codex или UI. `TranscriptSink` принимает снимок и возвращает ошибку записи.
- `rig_history.rs`: перевод сообщений Rig в общий формат, обратная проекция и hooks перед исполнением инструментов/после результата. Не владеет сессиями.
- `codex_history.rs`: свёртка `item/started`/`item/completed` и итоговых items App Server. Сохраняет идентичность и порядок; повторное завершение не добавляет дубль.
- `conversation.rs`: привязывает sink к конкретным session/run/parent; завершает ответ вместе со статусом запуска и привязкой Codex.
- `sessions.rs` / `session_store.rs`: валидация и транзакции. Только работающий запуск может менять свой промежуточный снимок. После завершения, отмены или сбоя содержимое неизменяемо.
- `transcript.ts`: одна проекция для немедленного ответа и загрузки истории; соединяет вызов с результатом по ID. `ToolHistory.tsx` только показывает данные, ничего не исполняет.

## Формат

В `SessionMessage.parts` сохраняются `text`, `reasoning`, `tool-call`, `tool-result`, а также непрозрачные `extension` для неизвестных provider items.

```json
[
  {"kind":"tool-call","data":{"callId":"call_1","name":"lookup","arguments":{"query":"пример"}}},
  {"kind":"tool-result","data":{"callId":"call_1","output":{"count":0},"isError":false}}
]
```

ID ограничен одним ответом. Параллельные вызовы могут возвращать результаты в другом порядке. Результат без вызова, повторный ID или повторный результат отклоняются. JSON `null`, `false`, числа, массивы и Unicode сохраняются без преобразования в строку или обрезки. Успешное завершение требует результата для каждого вызова; промежуточный снимок допускает незавершённые вызовы.

`extensions.replay.rig-v1` хранит полные сериализованные сообщения Rig: границы модельных шагов, native blocks, origin, ID, имена инструментов, типы результатов и ошибки. `PromptResponse.messages` содержит prompt и все добавления текущего запуска; prompt не дублируется в ответе Minerva. Для последующего API-запроса сообщения десериализуются обратно в Rig, а не собираются из `output()`. Если инструмент доступен текущему агенту, Rig отправляет нативные tool-call/result и их ID. Для инструментов, отсутствующих в текущем каталоге, Rig 0.46 переводит вызовы и результаты в текстовый контекст. Это проверено на всех трёх протоколах; структурированный оригинал в базе сохраняется.

`extensions.replay.codex-items-v1` сохраняет исходные items Codex, включая поля, не показанные в карточке. Общая проекция охватывает команды, MCP/dynamic tools, изменения файлов, поиск, изображения, ожидание и вызовы подагентов. Неизвестные items остаются доступными как данные провайдера.

## Сохранение и восстановление

SQLite v4 сохраняет существующие таблицы и данные v1–v3. Версия повышена из-за нового контракта содержимого и промежуточных ответов: старый бинарник должен отказать в открытии вместо потери данных.

Во время запуска сохраняется заменяемый снимок assistant-сообщения с тем же ID, который резервирует `runs`. Каждая запись — транзакция. Окончательное сообщение, статус `completed` и integration state коммитятся вместе. `session_load` добавляет актуальный `extensions.execution` из журнала запусков; при старте незавершённые запуски становятся `interrupted`.

Rig hook сохраняет принятый модельный шаг до инструментов и полученный результат до следующего запроса. Ошибка sink останавливает дальнейшее выполнение. Codex сохраняет наблюдаемые границы items, включая итоговые items неуспешного хода. Окно между внешним действием и доставкой его результата неустранимо локальной базой: если результата нет, карточка показывает «Результат не получен», а не успех.

После ошибки/отмены frontend перечитывает сохранённый снимок. Следующее сообщение ссылается на него, поэтому известные результаты не выпадают из ветки. Восстановление не вызывает инструменты. При отправке незавершённой истории в Rig отсутствующий результат закрывается **только в контексте нового запроса** явной ошибкой «состояние выполнения неизвестно»; в базе поддельного результата нет.

## Границы этапа

- Это снимки исполнения, не полный append-only журнал всех дельт. Частичный stdout и текст между границами items пока не гарантированно переживают аварийное завершение. Потоковый транспорт остаётся следующим этапом.
- Обычный путь Rig ещё не регистрирует оболочку как инструмент. Сохранение инструментального цикла проверено настоящим Rig с локальным тестовым инструментом; подключение плагинных инструментов и policy/approval — отдельный этап.
- Продолжение Codex использует подтверждённый remote thread. При создании нового thread передаётся текстовый transcript с JSON-частями, включая инструменты; это не точное восстановление удалённой сессии App Server.
- Бинарные вложения, usage, compaction, пагинация и долгоживущий App Server не входят в эту итерацию.
- Настоящий пользовательский Codex, платные модели и рабочая БД не использовались в тестах. Проверка React выполнена с тестовым IPC, отдельно от SQLite/Rig-тестов.

## Проверки

- Настоящий цикл Rig через локальный HTTP: вызов → результат → отказ следующего запроса → закрытие/открытие SQLite → новый HTTP-запрос с прежними call ID и результатом.
- Параллельные результаты, ошибка инструмента, JSON null/Unicode, неизменяемость завершённого ответа, прерванный снимок после перезапуска, запрет завершения с незакрытым вызовом.
- Вызовы Codex в другом порядке и повторные `item/completed`.
- Одинаковая frontend-проекция сразу после IPC и после загрузки; восстановление после ошибки, сохранение связи следующего сообщения, отмена без автоматического исполнения.
- Браузер: раскрытие ошибки, длинное имя инструмента, незавершённый вызов, продолжение диалога и переключение сессий с восстановлением карточек.
