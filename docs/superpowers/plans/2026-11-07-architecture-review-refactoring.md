# Аудит архитектуры и план рефакторинга — 2026-11-07

> Для исполнения по этапам: использовать superpowers:executing-plans. Это план по результатам ревью, а не отметка о выполненном рефакторинге.

**Цель:** базовый Minerva без встроенного Codex, поддерживаемый фронтенд и автоматические проверки качества.

**Уточнение пользователя после аудита:** встроенный Codex удалить сейчас; сохранение/миграция его истории не требуются. Реализация внешнего Codex-пакета и нового engine protocol не является условием удаления. Описанные ниже сохранение Codex resume state и миграционная приёмка этапа E отменены этим уточнением. Остальные пункты остаются отдельным планом, не частью удаления Codex.

**Выполненное удаление:** убраны Codex backend/history adapter, регистрация, HTTP/Tauri/gateway команды и capabilities, клиентские DTO, UI/preferences wiring и CSS. Перегенерированы контракты; убрана отдельная Windows-зависимость интеграции. Общая схема истории и её миграции оставлены, но v1 Codex resume state больше не переносится. Файлы пользовательских данных не удалялись.

**Проверки после удаления:** 46 JS-тестов, Rust workspace tests, строгий Clippy, rustfmt, contracts:check и frontend build прошли. Web E2E на отдельной копии свежего бинарника прошёл шаги отправки, reload, синхронизации модели и закрытия вкладки, затем упал на ожидании `.message-interrupted` после отмены. Полный E2E не пройден; причина этого сбоя в рамках удаления не установлена. Стандартная команда E2E не смогла заменить запущенный `target/debug/minerva-server.exe`; пользовательский процесс не останавливался. Общий рефакторинг и подключение frontend lint ещё не выполнены.

**Архитектура:** runtime владеет сессиями, сохранением и жизненным циклом выполнения; подключаемый движок владеет своим протоколом, моделями и специфичными настройками. Приложение собирает страницы и расширения через публичные контракты. Фронтенд разделяется по задачам, без обязательного заполнения всех слоёв FSD.

**Стек:** существующие Rust, SQLite, Cordis, React, assistant-ui, Tauri, Vite, Tailwind/PostCSS. Никакой замены стека ради рефакторинга.

**Основание:** запрос пользователя; текущие README, MODEL-ARCHITECTURE.md, docs/core-refactoring-plan.md и фактический код. Старые планы не считаются доказательством реализации.

## Область ревью

Minerva — локальный/web harness для диалогов с моделями, с Tauri-оболочкой и разрабатываемой hosted-платформой. Основной сценарий оценки: один пользователь, несколько сессий, возможны отдельные локальные конфигурации. Для hosted рассматриваются архитектурные границы, но здесь не проводится полная приёмка многопользовательской безопасности.

Подробно проверены связи runtime → Codex/providers/plugins, сохранение результата в conversation, bootstrap клиента, App/Chat/settings, модели клиента, контракты и основные SDK-механизмы. Выборочно прочитаны plugin host, credential store, network policy, HTTP/Tauri entry points и тесты. Это не построчный аудит всех crates.

## Исправить в первую очередь

### 1. Локальные конфигурации разделяют API-ключи

**Где:** `crates/runtime/src/credential_store.rs:28`, `crates/runtime/src/providers.rs:61`, `crates/runtime/src/plugins.rs:234`.

**Что происходит:** LocalKeyring адресует запись только по имени провайдера и игнорирует CredentialScope; локальный bootstrap вызывает ProviderService::new с фиксированным `local`. Два каталога `--config-dir` с одним ID `openai` используют одну запись ОС. Сохранение или удаление ключа в B меняет ключ для A; при разных endpoint один профиль способен использовать ключ другого.

**Минимальное исправление:** стабильная идентичность локального профиля входит в адрес записи keyring и передаётся bootstrap → ProviderService → CredentialStore. Одного включения tenant/workspace недостаточно: локальный server фиксирует `local/default` даже для разных config-dir. Для прежних записей нужен явный перенос в старый профиль, без глобального fallback каждого нового профиля.

**Если оставить:** взаимная порча настроек и возможная отправка ключа на endpoint другой конфигурации. Тест MemoryCredentialStore уже проверяет scope, но не доказывает правильность production LocalKeyring. Вывод получен по коду; рабочие ключи не читались и сценарий с ними не запускался.

## Исправить до дальнейшего расширения

### 2. Codex является частью ядра, а не устанавливаемым расширением

**Где:** `crates/runtime/src/lib.rs:1`, `plugins.rs:280`, `conversation.rs:161`; `crates/api/src/rpc.rs:259`; `src-tauri/src/main.rs:140`; `crates/contracts/src/main.rs:3`; `packages/client/src/types.ts:27`.

**Что происходит:** runtime безусловно компилирует Codex, manager создаёт сервис, orchestration знает префикс модели, формат options, namespace и threadId. HTTP, Tauri и общий генератор типов содержат отдельные Codex-команды. На hosted сервис заменён unavailable-реализацией, но код остаётся частью зависимости.

**Минимальное исправление:** нейтральный контракт движка и подключение через существующий process host; реализацию Codex, его wire DTO и UI вынести в независимо собираемый пакет. Feature flag допустим только как переходный этап, но не соответствует конечному требованию пользователя.

**Если оставить:** любое изменение Codex требует пересборки программы; новый движок добавляет очередные ветки в ядро. Наличие исходников в монорепозитории само по себе не означает включения в бинарник, но здесь есть прямые зависимости. Конечная цель для Codex — отдельная поставка исходников/пакета, основной репозиторий содержит только нейтральный SDK и фикстуры.

### 3. Текущий SDK ещё не позволяет просто вынести Codex наружу

**Где:** `crates/plugin-sdk/src/lib.rs:69`, `crates/plugin-host/src/lib.rs:346`, `apps/web/src/app/plugins.tsx:8`.

**Что происходит:** manifest запрещает ID `codex`; process call ожидает единственный ответ с совпадающим ID, не является каналом checkpoints выполнения. Browser composition статически импортирует CodexSettings. Универсальный `plugins.call` не интегрирован как движок сохранённого запуска.

**Минимальное исправление:** добавить только необходимый контракт engine run/cancel/checkpoint/result и capability моделей; типы UI-вкладов разместить в SDK. Подключить загрузку установленного UI с проверкой совместимости. Сохранение, авторизация, отмена и подтверждение результата остаются у host.

**Если оставить:** перенос файлов либо сломает Codex, либо создаст второй обходной путь выполнения без гарантий истории. Существующий plugin host следует расширить, а не писать новый параллельный framework.

### 4. Разделение страниц не разделило ответственность

**Где:** `apps/web/src/app/App.tsx:24`, `apps/web/src/pages/chat/Chat.tsx:17`, `:76`, `apps/web/src/pages/settings/Settings.tsx`.

**Что происходит:** App управляет сессиями, выбором модели, Codex preferences и жизненным циклом UI-плагинов. Chat одновременно содержит оболочку приложения, навигацию, settings/plugins, рендер сообщений и управление runtime. Страницы импортируют `app/models` и `app/plugins`, хотя app уже импортирует страницы; корневые Settings/Plugins/CodexSettings — дополнительные re-export-файлы, а не независимые реализации.

**Минимальное исправление:** app оставляет bootstrap/composition; оболочка собирает страницы; chat владеет своим адаптером истории и синхронизацией. Контексты и публичные plugin slot props доступны через SDK/нижний слой. Состояние Codex уходит вместе с плагином. Shared содержит только действительно общие примитивы.

**Если оставить:** изменение настроек расширения затрагивает bootstrap и чат; переносы между папками дают видимость архитектуры без уменьшения связности. Не нужно превращать каждую функцию в utility или создавать все семь FSD-слоёв.

### 5. Стили накапливают переопределения в одном глобальном файле

**Где:** `apps/web/src/style.css`, `postcss.config.cjs`, `tailwind.config.cjs`.

**Что происходит:** большой первоначальный блок правил ниже переопределяется блоком `Calm, content-first chat treatment`, затем в тот же файл добавлены plugins, shell и settings. Например, `.sidebar`, `.composer`, `.message` и цвета имеют несколько источников. Изменение раннего правила может не проявиться из-за следующего блока.

**Минимальное исправление:** сначала форматировать, затем свести дублирующиеся декларации с сохранением cascade/media behavior; оставить глобально tokens/reset/base, перенести оформление владельцам. Использовать CSS Modules для локальных правил и существующие Tailwind/shadcn примитивы. Portal-компоненты должны получать theme tokens явно либо из общего корня.

**Если оставить:** правки интерфейса становятся зависимыми от порядка глобальных правил; стили расширений могут конфликтовать. PostCSS, Tailwind и Autoprefixer уже подключены. Отсутствие Sass не является дефектом; добавлять его без конкретной задачи не нужно.

### 6. Frontend не имеет автоматического стандарта оформления и проверки импортов

**Где:** `package.json`, `tsconfig.json`, `apps/web/vite.config.ts`, `apps/web/src/app/App.tsx`.

**Что происходит:** build выполняет TypeScript/Vite, но нет lint/format scripts и конфигураций ESLint/Prettier. JSX и обработчики сжаты в длинные строки; есть оставшиеся импорты вроде createRoot в App/Chat. TypeScript strict не заменяет проверку hooks или границ архитектуры.

**Минимальное исправление:** Prettier для оформления; ESLint + TypeScript/React Hooks для ошибок, неиспользуемых импортов и запрещённых зависимостей. rustfmt и Clippy сохранить. Механическое форматирование отдельным изменением, исправления hooks — отдельным, с проверкой поведения.

**Если оставить:** новые файлы продолжают расходиться по стилю, а ревью тратится на чтение длинных строк. Не включать автоисправление dependencies hooks без анализа: оно может поменять число запросов и поведение эффектов.

### 7. Тестовый Cordis-плагин запускается в обычной программе

**Где:** `crates/runtime/src/plugins.rs:27`, `:264`.

**Что происходит:** ExamplePlugin и health counter присутствуют в production manager; `start_example` вызывается при bootstrap, элемент отображается в обычном roster. `cfg(test)` стоит только на части вспомогательного доступа, а не на самом плагине.

**Минимальное исправление:** перенести lifecycle-пример в тестовую fixture; оставить устанавливаемый `plugins/review-example` отдельной демонстрационной поставкой. Проверить тесты roster и документацию.

**Если оставить:** демонстрационная функциональность постоянно усложняет production lifecycle и список обязательств менеджера.

### 8. Один долгий вызов блокирует управление всеми внешними плагинами

**Где:** `crates/runtime/src/plugins.rs:323`, `crates/plugin-host/src/lib.rs:574`.

**Что происходит:** manager удерживает общий mutex external host во время await вызова процесса; Host::call требует `&mut self`. Пока плагин A не ответит или не истечёт deadline, вызовы B и операции roster/toggle, которым нужен этот mutex, ждут.

**Минимальное исправление:** до подключения долгих engine runs оставить общий lock только для registry, сериализовать RPC на уровне конкретного процесса. Для cancel нужен управляемый отдельный путь, не ожидающий окончания run под тем же lock.

**Если оставить:** вынесенный Codex будет задерживать управление остальными расширениями на время ответа. Для текущего короткого review-example это не доказанная проблема производительности, но конкретный блокер использования этого host для движков.

### Этап E. Нейтральный engine contract и отдельный Codex

**Затрагивает:** runtime conversation/transcript/session integration; plugin-sdk/plugin-host; API/Tauri dispatcher; contracts generator/client types; client-models/providers; app/plugins/App; CodexSettings; tests и сборочные manifest. `codex.rs` и `codex_history.rs` переносятся вместе с реализационными тестами.

- [ ] Сначала зафиксировать тестами текущие гарантии: checkpoint сохраняется до публикации, финальный ответ атомарен с integration state, cancel освобождает запуск, неуспешный ход не оставляет пригодный resume state.
- [ ] Ввести нейтральную регистрацию движка по namespace. Host получает catalog/capabilities, отправляет run с сохранённой веткой и opaque replay state; процесс возвращает checkpoints и result. Cancel адресуется run ID. Встроенный API/Rig адаптер использует тот же контракт.
- [ ] Вынести `matching_codex_thread`, CodexOptions и знание threadId из conversation. Ядро проверяет привязку opaque state к успешно сохранённому ответу и сохраняет его атомарно, не переписывая состояние под Codex.
- [ ] Расширить process protocol для этих сообщений с версией, лимитами, валидацией run IDs и завершением при нарушении протокола; убрать общий host lock из ожидания ответа процесса.
- [ ] Собрать отдельный Codex backend/UI пакет вне базовой поставки. Убрать reserved ID только вместе с удалением builtin. Перенести настройки/модели/авторизацию и Codex DTO из общего клиента в пакет.

## Обоснование инструментов

Prettier отвечает за форматирование, ESLint — за качество кода: [официальное разделение обязанностей](https://prettier.io/docs/integrating-with-linters). React Hooks plugin проверяет правила hooks и dependencies: [React docs](https://react.dev/reference/eslint-plugin-react-hooks). Статические ограничения импортов можно выразить через [no-restricted-imports](https://eslint.org/docs/latest/rules/no-restricted-imports); динамическую загрузку расширений дополнительно проверяют интеграционные тесты.

FSD использован как правило направленности зависимостей и группировки по ответственности, а не как обязательный шаблон дерева: `.agents/skills/fsd-docs/references/03-cross-imports-and-antipatterns.md`.

**Вердикт:** тестовая база уже полезна; главный долг — реальные границы расширений, production scope секретов и распределение ответственности frontend. Начать с отдельного форматирования и исправления ключей, затем развязывать UI и engine contract.

**Упрощение:** убираются production ExamplePlugin, корневые re-export-прокладки и Codex-ветки ядра; точное сокращение строк/зависимостей до реализации не оценивалось. Перенос кода в другой пакет не равен удалению кода.

**Не проверено:** GUI/Tauri вручную, web E2E в этом прогоне, реальные Codex/login/model calls, рабочие секреты, Linux/macOS и hosted deployment целиком. Основной риск исполнения плана — потеря гарантий истории или доступа к старым ключам при механическом переносе без миграционных тестов.
