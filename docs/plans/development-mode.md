# Режим разработки

Отдельный режим компоновки: дерево проекта слева, вкладки документов в центре,
существующий диалог справа. Переключение режима сохраняет runtime диалога и черновик.
Компоненты оболочки — существующие shadcn Sidebar и Resizable; редактор — Monaco.

## Порядок работ

1. Добавить API каталога и документов в общий Runtime и оба транспорта. Путь
   разрешается относительно проекта активной сессии; интерфейс не получает
   произвольный доступ к файловой системе.
2. Чтение возвращает содержимое и версию. Запись принимает ожидаемую версию и
   выполняется атомарно; при изменении файла снаружи сообщает о конфликте.
   Проверить одновременные изменения пользователем и агентом, ссылки и границы папки.
3. Добавить модели Monaco с отдельными состояниями вкладок, грязным буфером,
   сохранением и подтверждением закрытия. Подключить workers через Vite и проверить
   их в собранном Tauri, а не только в браузере разработки.
4. Встроить дерево и редактор в независимую компоновку, оставив один экземпляр
   runtime диалога. Привязать состояние вкладок и выбранный проект к workspace.
5. Проверить переходы режимов, несколько вкладок, конфликты записи, смену проекта,
   перезагрузку, работу диалога во время редактирования и узкие окна.

Существующие `read_file`/`write_file` — инструменты агента, они не являются
готовым пользовательским файловым API: чтение ограничено 64 КиБ и не возвращает
версию для проверки конкурентной записи. Нужен отдельный контракт с общими
правилами доступа и записи, а не вызов shell для операций редактора.

## Готовые компоненты

- [Monaco](https://github.com/microsoft/monaco-editor) — редактор, модели и diff;
  проверить workers в Vite и установленном Tauri.
- [ignore](https://github.com/BurntSushi/ripgrep/tree/master/crates/ignore) —
  обход файлов и поиск с правилами `.gitignore`; не подменяет границу доступа.
- [notify](https://github.com/notify-rs/notify) — наблюдение за изменениями;
  учитывать потери событий и сетевые файловые системы, повторно проверять версию.
- [portable-pty](https://docs.rs/portable-pty/latest/portable_pty/) и
  [xterm.js](https://github.com/xtermjs/xterm.js) — серверная PTY и визуальный терминал.
- [monaco-languageclient](https://github.com/TypeFox/monaco-languageclient) —
  возможная интеграция LSP после базового редактора; согласовать версии зависимостей.
- [similar](https://docs.rs/similar/latest/similar/) — текстовый diff и three-way merge;
  не заменяет журнал изменений агента и проверку версии файла.

Уже используем `cap-std`, `sha2` и атомарную замену. Вынести общие операции
из native-инструментов в сервис и использовать одинаковые правила для UI и агента.
Подключать новые библиотеки по этапам после проверки лицензий, совместимости
и поведения на Windows. Это кандидаты: интеграция ещё не проверена.

## Системный плагин LSP

Добавить системный Cordis-плагин `lsp` с сервисом `studio.lsp`. Его жизненный
цикл принадлежит Runtime; процесс конкретного языкового сервера привязан к
проекту и конфигурации сервера. Клиенты получают доступ через общий контракт
Runtime для desktop и web, с проверкой доступности выбранного проекта. Hosted
профиль не должен запускать сервер на машине браузера: выполнение возможно только
там, где у Runtime есть явно настроенный проект и доступный сервер.

- Каталог серверов содержит язык, команду, аргументы и настройки. Отображать
  состояние: доступен, запускается, работает, ошибка, сервер не найден.
- Сервис запускает, останавливает и перезапускает процессы, завершает их при
  закрытии проекта/Runtime и изолирует ошибку одного сервера от остальных.
- Monaco подключается через адаптер LSP; изучить `monaco-languageclient` и
  согласовать версии с Monaco. Транспорт и проверка доступа должны использовать
  существующую модель авторизации Host; отдельный открытый порт не подразумевается.
- Синхронизировать `didOpen`, `didChange`, `didSave`, `didClose`, версии и URI
  документов; сервер должен видеть несохранённый буфер. Ограничить и проверить
  переходы, предложенные сервером, границами проекта.
- На первом этапе: диагностика, hover, переход к определению и автодополнение;
  rename, форматирование и code actions — после проверки применения правок к
  нескольким файлам с учётом несохранённых изменений и конфликтов версий.
- Тесты: два проекта, разные серверы и клиенты; порядок и версия изменений;
  Unicode и пути Windows; закрытие документа, смена проекта, сбой/перезапуск,
  завершение процессов, отказ при недоступном сервере и ограничения hosted.

На этапе проверки использовать уже установленный языковой сервер из явно заданной
конфигурации. Фактическая совместимость Monaco/LSP и работа в Tauri пока не доказаны.

### Готовые LSP-клиенты и изоляция проектов

Кандидат для первого технического эксперимента —
[tokio-lsp-client](https://docs.rs/tokio-lsp-client/latest/tokio_lsp_client/):
предоставляет клиент, запуск из `tokio::process::Command` и типы протокола.
Наш GitHub-форк для возможных исправлений:
[minerva-harness-tokio-lsp-client](https://github.com/kviron/minerva-harness-tokio-lsp-client).
При необходимости доработок сохранять связь с upstream и использовать префикс
`minerva-harness` для своих веток и именуемых изменений.
Версия 0.0.1; заявления о соответствии протоколу и тестах исходят от авторов,
совместимость, зрелость и лицензию нужно проверить до выбора зависимости.
[async-lsp](https://github.com/oxalica/async-lsp) также поддерживает обе стороны
протокола и упорядочивает уведомления, но является более низкоуровневой основой.
[helix-lsp](https://github.com/helix-editor/helix/blob/master/helix-lsp/Cargo.toml)
— пример работающего клиента, однако связан с внутренними crates Helix и его
лицензией MPL-2.0. Для Monaco остаётся вариант
[monaco-languageclient](https://github.com/TypeFox/monaco-languageclient): в этом
случае Rust управляет процессом и транспортом, а клиент протокола находится в UI.
Не создавать второй полноценный LSP-клиент параллельно; выбрать вариант после spike.

Rust-клиент/транспорт не заменяет сами языковые серверы: например,
[rust-analyzer](https://rust-analyzer.github.io/book/rust_analyzer_binary.html)
нужен отдельно. Управлять существующей установкой и её конфигурацией.

В `studio.workspaces` проект-папка и scope авторизованного Host — разные
сущности. Получать ID проекта и канонический корень на стороне Runtime из
реестра и членства сессии, не принимать произвольный `cwd` от интерфейса.
Разделять экземпляры как минимум по `(host scope, workspace ID, server ID,
конфигурация)`; задать процессу рабочий каталог и LSP root URI этого проекта.
Серверы с разными корнями или настройками не переиспользуются автоматически.
Несколько диалогов одного проекта могут совместно использовать сервер при
согласованном жизненном цикле документов. Несохранённые несовпадающие буферы
одного файла из разных клиентов требуют отдельной политики: нельзя молча слить
их версии в один поток `didChange`.

Spike до выбора архитектуры: поднять тестовый LSP и два реальных каталога,
проверить initialize/root URI, изоляцию диагностик и конфигурации, didOpen/
didChange/didClose с версиями, ответы сервера на запросы к клиенту, отмену,
ошибки, остановку и перезапуск процесса, а также работу на Windows в Tauri и
через авторизованный web Host. Решение по общей логике сервиса и UI-клиенту
принимать по результатам этого эксперимента.

Первый эксперимент (Windows): `tokio-lsp-client 0.0.1` собрался и одновременно
инициализировал два процесса тестового сервера с разными `cwd` и `workspaceFolders`,
после чего оба прошли `shutdown`/`exit`. Код и fixture находятся в игнорируемой
папке `agent-artifacts/lsp-spike`; команда: `cargo run --manifest-path
agent-artifacts/lsp-spike/Cargo.toml`. Проверен только тестовый сервер: диагностика,
версии документов, реальные серверы, отказ процессов и интеграция с приложением
ещё не проверены. Локальный Rust toolchain не содержит компонент rust-analyzer.
`tokio-lsp-client`: MIT, требует Rust 1.88, помечен как passively-maintained.


Системный плагин `mh-lsp` подключён к Runtime через форк
`kviron/minerva-harness-tokio-lsp-client` с закреплённым коммитом. В текущем
срезе он управляет локальным процессом rust-analyzer отдельно для каждого проекта;
путь берётся из реестра workspace. При удалении проекта процесс останавливается.
Это основа жизненного цикла, а не готовая интеграция с редактором: обработка
серверных запросов и диагностик, синхронизация документов и Monaco ещё не
реализованы. Доступность и поведение реального rust-analyzer требуют проверки.


`mh-lsp-rust` — отдельный встроенный системный плагин: регистрирует в
`mh.lsp` сервер `rust-analyzer` и расширение `.rs`. Реестр принимает другие
нативные Rust-плагины через `LspService::register`; дубликаты ID и расширений
отклоняются, при выгрузке регистрация и процессы этого провайдера удаляются.
Процессы разделены по workspace и ID провайдера. API внешних установленных
плагинов для регистрации языков пока не реализован.


Проверка транспорта выявила гонку между записью запроса и регистрацией
ожидания ответа, а также потерю сообщений из-за пересоздания `BufReader` и
отмены чтения при сообщениях stderr. Исправления исследуются в локальном
клоне `agent-artifacts/mh-lsp-client` на ветке `mh-fix-request-race`;
зависимость Harness всё ещё закреплена на прежнем коммите, исправления ещё не
опубликованы. Необходимо обработать неизвестные запросы сервера и проверить
жизненный цикл stderr и отмены.

В `mh-lsp` добавлена обработка `workspace/configuration`,
`workspace/workspaceFolders`, `window/workDoneProgress/create` и сохранение
диагностик; тестовый сервер проверяет ответ и публикацию диагностик. API для
установленных плагинов, синхронизация документов и доступ редактора к
диагностикам ещё не готовы.
